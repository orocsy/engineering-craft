# Evidence patterns from real deliveries

| Symptom | Discriminating evidence | Fix or stop condition |
|---|---|---|
| Image returns 4xx despite available original | Compare original bytes, actual MIME and encoded response envelope against deployed provider limits | Prepare bounded web derivatives, preserve protected originals and verify withdrawn images stay unavailable |
| First paint is stable but main visual is slow | Compare document arrival, image discovery, byte transfer and paint. Record the LCP element in both versions | Give the actual first-screen image early discovery and suitable bytes. Avoid preloading every variant |
| The initial HTML contains the eager image, but its request still starts late | Measure the bytes before the image tag. Inspect serialized component props and repeated data before assuming a JavaScript execution delay | Pass only fields the interactive component reads. Replay both built documents with paced HTML and identical assets. Verify the visible HTML, canonical and structured data, historical fallbacks, and browser interactions |
| Image request starts earlier but the page paints later | Compare the same stylesheet bytes in both traces. Check request priority, HTTP version, connection IDs and reuse for CSS and image requests. A local replay can omit the production connection wait | Judge FCP, LCP and the complete user journey. If critical CSS is delayed enough to worsen page paint under matched conditions, withdraw the change and verify the previous program with current content |
| A tiny image still takes seconds | Compare DNS, TCP/TLS, request queue, first byte and body. When possible, join the same request ID to gateway duration and application spans | Separate measured service time from the remainder. Reduce demonstrated waiting. Preserve authorization and avoid new infrastructure based on one sample |
| Same code yields a larger archived CSS bundle | Build both with actual dependencies, compare scanned files and byte hashes | Exclude generated/dependency sources explicitly and verify intended styles survive |
| Shared CSS blocks the first paint | Inspect actual transfer encoding, bytes and the elapsed request. Replay one measured change at a time. For an isolated route style, build both versions and compare the common stylesheet digest, hydrated UI and screenshots. | Verify compression or scoping on the actual host. Try conditional GET and a cold and warm navigation. If cache headers also appear on 404s, confirm the failure cache lifetime before setting a long policy. |
| Page returns 200 but CSS or JavaScript returns 404 during a release | Keep both exact deploy packages. Use a browser with an empty cache to serve old HTML with new assets and new HTML with old assets. Check computed styles and asset digests | Serve new immutable assets before switching the document. Keep old assets available on the new release and keep a rollback revision that serves both sets. Verify the transition and the settled site separately |
| New sizes exist but browser downloads full files | Inspect the initial HTML, alternate product/configuration images, browser-selected URL and decoded image | Preserve normalized hints across build, refresh and recovery. Verify existing interactions as regression checks |
| Browser upload succeeds but takes minutes | Isolate browser PUT, object availability, conversion and registration. Retain the status and bounded provider error code while omitting signed addresses and raw replies | Compare the same file and upload destination across the affected networks. Test first-upload speed and recovery from a lost reply as separate cases |
| The browser loses the final upload response | Arrange for the real storage endpoint to accept one test file, then drop its success response at the browser. Verify how many objects and application records the retry produces | Check the existing authorized object before resending. Finalize it if it matches. Resend to the same upload intent if the file is absent. Verify the private preview, public denial and cleanup |
| Cloud build submission fails after sending the package | Time the sender finishing the request, the provider replying, the build and the live version switch separately. Check actual provider versions before retrying | Keep the complete release archive. Reuse confirmed immutable assets only when provenance and bytes can be checked during the build. Verify live output as well as the transfer result |
| A/B results change with region, device or runtime | Compare exact matched settings and raw samples; use a control and alternate conditions | Label confounds. Do not roll back an otherwise correct fix based only on mixed-location medians |
| Browser replay reports impossibly fast injected media | Check body-byte count and observed elapsed time against shaping rate | Route-injected responses can bypass network emulation. Use a real HTTP response with paced bytes or a verified shaper |
| CI is green but users still see the old behavior | Read live asset, runtime and configuration independently | Separate publication, feature activation, public acceptance and later field/platform results |

Incidents and measurements: [Channel image repair](https://github.com/vibelingan/channel/actions/runs/43752358379), [mobile Lighthouse comparison](https://github.com/vibelingan/channel/actions/runs/43779782125), [catalog image timing rollout](https://github.com/vibelingan/channel/actions/runs/44334875275) and [US transport results](https://github.com/vibelingan/channel/actions/runs/44335663143). Vendor limits and measured timings are versioned evidence, not universal rules. When updating sources, pin the code reviewed, preserve older contradictory evidence, and rerun a representative probe before changing guidance.

## Choosing outside guidance

Verify the measured layer before adapting a framework recipe. For Chromium tooling and general web checks, see [Web Quality Skills at afa8da9](https://github.com/addyosmani/web-quality-skills/tree/afa8da942115f2961fdbfa80807ea0b232ff6c00). For React code evidenced by a component profile, see [Vercel Agent Skills at 1a2c79d](https://github.com/vercel-labs/agent-skills/tree/1a2c79d4e6c4a2283dc2c614b6538cbe1ed5ca62). For a server delay evidenced by request spans or CPU time, use [Node.js performance diagnostics](https://nodejs.org/en/learn/diagnostics/poor-performance) and the provider's own latency definitions. Confirm applicability to the installed framework and runtime before changing code.

A dated set of 15 cold-cache mobile measurements reproduced a useful stopping rule. A 16 KB product image needed only 89–118 ms for its response body after the first byte. The first byte took 1.14–1.23 s after the request. The service reported only 29–44 ms to look up the image record. Reducing the file or removing the lookup would address little of that observed delay. The next comparison should vary the request discovery or delivery path, retain the byte digest and visibility checks, and keep the rest of the page fixed.

In a [request-ID comparison](https://github.com/vibelingan/channel/commit/71308db1), three connection-reusing requests for that image took 1.48–2.73 s to receive the first byte, while the three corresponding gateway log entries recorded 0.47–0.62 s. Join each request before taking a difference and keep application time nested inside gateway time. The difference is time outside what the gateway measured. Identifying a particular network hop still requires its own evidence. Retain raw request IDs privately when they are not needed to reproduce the published numbers.

In one [production image-priority trial](https://github.com/vibelingan/channel/actions/runs/44424201310), cold mobile Chrome saw image discovery advance from 803 to 20 ms after the first HTML byte. The image reused a connection on the HTTP/1.1 delivery path; the unchanged stylesheet opened another connection of about 0.89 s. FCP moved from 3.37 to 4.24 s and LCP from 3.67 to 4.30 s. Three samples per version and an unchanged comparison page supported withdrawing the change. This pattern is transport-dependent. See [Chrome Network timing](https://developer.chrome.com/docs/devtools/network/reference/#timing-explanation) for the browser measurements.

In a [subsequent controlled test](https://github.com/vibelingan/channel/commit/67027d0d2e4694942f4b30effa6c5fcff6ceef45), an Astro product route embedded the old product and category-page data ahead of the eager image even when the page already had its current approved product detail. Removing unused data put the same image 7.9–9.1 KB earlier in the built HTML. With identical image and stylesheet responses, alternating six times at each of two HTML transmission rates, median LCP improved by 46 ms at 200 KB/s and 160 ms at 50 KB/s. Keep these effects separate from production delivery and verify them again there. [Astro framework component props](https://docs.astro.build/en/guides/framework-components/#passing-props-to-framework-components)


## Upload and deploy incidents

**Prove what the provider received.** A browser sent a 4.81 MB PNG to Shanghai COS. One run succeeded after 155 seconds, mostly while sending. A later run returned HTTP 400 and reported `UserNetworkTooSlow` after about 203 seconds. The second attempt in that same run reached storage, but the browser test intentionally intercepted its success and failed to complete the UI. That mixed two failure modes. Keep the 4.81 MB case for measuring the actual network. Use a much smaller file that still takes the normal preview path for the lost-success test, intercept the first upload's success, then assert that retry uses one application record and does not resend known saved bytes. If assessing resumable uploads, check the provider contract first. Tencent's single presigned PUT has no resume operation. [Channel run](https://github.com/vibelingan/channel/actions/runs/44487251177) · [Tencent presigned upload](https://cloud.tencent.com/document/product/436/14114)

The corrected production test used a 200,514-byte PNG and hid exactly one real HTTP 200 response. The administrator clicked Retry once. The browser sent one PUT in total, the website kept one image record, the signed-in preview decoded, and anonymous access returned 404. An independent storage listing confirmed both test directories were empty after cleanup. This test answers whether the UI can recover a saved upload. Compare large-file first-upload throughput with matching workloads and networks. [Verified production recovery](https://github.com/vibelingan/channel/actions/runs/44495550172)

**Measure one version transition.** A Blog source upload took roughly 307 seconds to finish writing on the sender and received HTTP 400 at 311 seconds. The provider did not register a new version. A previously approved, byte-identical 7.20 MB video accounted for most of the archive. The shorter transfer sent the other files and let the cloud builder download the identical public video and enforce its length and SHA-256 before writing it. The full source archive still contained every file for recovery. The next provider reply was HTTP 200 at about 41 seconds, and its build took about 74 seconds. Verify the public version and a byte range of the video separately. In this case old and new responses overlapped briefly even after the provider reported the new version. Eight later article and image reads returned the new version. An unknown or changed video should still be uploaded in full.
