# Evidence patterns from real deliveries

| Symptom | Discriminating evidence | Fix or stop condition |
|---|---|---|
| Image returns 4xx despite available original | Compare original bytes, actual MIME and encoded response envelope against deployed provider limits | Prepare bounded web derivatives, preserve protected originals and verify withdrawn images stay unavailable |
| First paint is stable but main visual is slow | Compare document arrival, image discovery, byte transfer and paint. Record the LCP element in both versions | Give the actual first-screen image early discovery and suitable bytes. Avoid preloading every variant |
| The initial HTML contains the eager image, but its request still starts late | Measure the bytes before the image tag. Inspect serialized component props and repeated data before assuming a JavaScript execution delay | Pass only fields the interactive component reads. Replay both built documents with paced HTML and identical assets. Verify the visible HTML, canonical and structured data, historical fallbacks, and browser interactions |
| Image request starts earlier but the page paints later | Compare the same stylesheet bytes in both traces. Check request priority, HTTP version, connection IDs and reuse for CSS and image requests. A local replay can omit the production connection wait | Judge FCP, LCP and the complete user journey. If critical CSS is delayed enough to worsen page paint under matched conditions, withdraw the change and verify the previous program with current content |
| Inlining a stylesheet improves text paint while the hero is slow | Compare the HTML and hero response intervals, bytes and paint time. Alternate old and candidate HTML with the same real asset endpoints before release. An in-memory HTML replay omits document transport, so retain a separate trace with a paced or real document response | Keep separate decisions for first paint and hero paint. Treat a shorter request delay or an isolated style replay as insufficient when full-page and matched-asset results show a slower hero |
| A tiny image still takes seconds | Compare DNS, TCP/TLS, request queue, first byte and body. When possible, join the same request ID to gateway duration and application spans | Separate measured service time from the remainder. Reduce demonstrated waiting. Preserve authorization and avoid new infrastructure based on one sample |
| A production archive has many files or a suspicious script name | Verify the accepted manifest, then inspect all public file paths and generated content for development markers. Compare current HTML references, prior releases and browser requests, including a relevant interaction | Fix a demonstrated entry or build leak. Keep assets required by cached tabs and fallback versions until their preservation or expiry is proven. Measure package size and browser bytes separately |
| Same code yields a larger archived CSS bundle | Build both with actual dependencies, compare scanned files and byte hashes | Exclude generated/dependency sources explicitly and verify intended styles survive |
| Shared CSS blocks the first paint | Inspect actual transfer encoding, bytes and the elapsed request. Replay one measured change at a time. For an isolated route style, build both versions and compare the common stylesheet digest, hydrated UI and screenshots. | Verify compression or scoping on the actual host. Try conditional GET and a cold and warm navigation. If cache headers also appear on 404s, confirm the failure cache lifetime before setting a long policy. |
| Page returns 200 but CSS or JavaScript returns 404 during a release | Keep both exact deploy packages. Use a browser with an empty cache to serve old HTML with new assets and new HTML with old assets. Check computed styles and asset digests | Serve new immutable assets before switching the document. Keep old assets available on the new release and keep a rollback revision that serves both sets. Verify the transition and the settled site separately |
| New sizes exist but browser downloads full files | Compare complete image GET, the approved product response, built HTML and the browser-selected URL. A binary endpoint can resolve pending visibility checks that the metadata endpoint skipped | Preserve the visibility check and read budget. Check that a withdrawn image still has no public hint, and inspect the candidate HTML before shipping. Verify that the browser downloads and decodes the intended size |
| Same small file, shorter request path, uncertain LCP | Alternate the existing and candidate URLs with the same HTML, verified response bytes, document origin and browser settings. Keep connection reuse, first byte, read completion and paint for each pair | Keep the current path when the candidate wins only occasionally or the gain does not cover its new complexity. Retain the negative result to avoid repeating the same trial |
| Browser upload succeeds but takes minutes | Isolate browser PUT, object availability, conversion and registration. Retain the status and bounded provider error code while omitting signed addresses and raw replies | Compare the same file and upload destination across the affected networks. Test first-upload speed and recovery from a lost reply as separate cases |
| The browser loses the final upload response | Arrange for the real storage endpoint to accept one test file, then drop its success response at the browser. Verify how many objects and application records the retry produces | Check the existing authorized object before resending. Finalize it if it matches. Resend to the same upload intent if the file is absent. Verify the private preview, public denial and cleanup |
| Cloud build submission fails after sending the package | Time the sender finishing the request, the provider replying, the build and the live version switch separately. Check actual provider versions before retrying | Keep the complete release archive. Reuse confirmed immutable assets only when provenance and bytes can be checked during the build. Verify live output as well as the transfer result |
| A/B results change with region, device or runtime | Compare exact matched settings and raw samples; use a control and alternate conditions | Label confounds. Do not roll back an otherwise correct fix based only on mixed-location medians |
| Browser replay reports impossibly fast injected media | Check body-byte count and observed elapsed time against shaping rate | Route-injected responses can bypass network emulation. Use a real HTTP response with paced bytes or a verified shaper |
| CI is green but users still see the old behavior | Read live asset, runtime and configuration independently | Separate publication, feature activation, public acceptance and later field/platform results |

Incidents and measurements: [Channel image repair](https://github.com/vibelingan/channel/actions/runs/43752358379), [mobile Lighthouse comparison](https://github.com/vibelingan/channel/actions/runs/43779782125), [catalog image timing rollout](https://github.com/vibelingan/channel/actions/runs/44334875275) and [US transport results](https://github.com/vibelingan/channel/actions/runs/44335663143). Vendor limits and measured timings are versioned evidence, not universal rules. When updating sources, pin the code reviewed, preserve older contradictory evidence, and rerun a representative probe before changing guidance.

## Choosing outside guidance

Verify the measured layer before adapting a framework recipe. For Chromium tooling and general web checks, see [Web Quality Skills at afa8da9](https://github.com/addyosmani/web-quality-skills/tree/afa8da942115f2961fdbfa80807ea0b232ff6c00). For React code evidenced by a component profile, see [Vercel Agent Skills at 1a2c79d](https://github.com/vercel-labs/agent-skills/tree/1a2c79d4e6c4a2283dc2c614b6538cbe1ed5ca62). For a server delay evidenced by request spans or CPU time, use [Node.js performance diagnostics](https://nodejs.org/en/learn/diagnostics/poor-performance) and the provider's own latency definitions. For a change worth shipping, record which source and rule fit each observation, the local counterexample or limitation, and the check that decided it. Compare plausible competing changes against the same baseline. Put the measured evidence in the project, and carry the rule plus its conditions back into the skill.

A dated set of 15 cold-cache mobile measurements reproduced a useful stopping rule. A 16 KB product image needed only 89–118 ms for its response body after the first byte. The first byte took 1.14–1.23 s after the request. The service reported only 29–44 ms to look up the image record. Reducing the file or removing the lookup would address little of that observed delay. The next comparison should vary the request discovery or delivery path, retain the byte digest and visibility checks, and keep the rest of the page fixed.

In a [request-ID comparison](https://github.com/vibelingan/channel/commit/71308db1), three connection-reusing requests for that image took 1.48–2.73 s to receive the first byte, while the three corresponding gateway log entries recorded 0.47–0.62 s. Join each request before taking a difference and keep application time nested inside gateway time. The difference is time outside what the gateway measured. Identifying a particular network hop still requires its own evidence. Retain raw request IDs privately when they are not needed to reproduce the published numbers.

In one [production image-priority trial](https://github.com/vibelingan/channel/actions/runs/44424201310), cold mobile Chrome saw image discovery advance from 803 to 20 ms after the first HTML byte. The image reused a connection on the HTTP/1.1 delivery path; the unchanged stylesheet opened another connection of about 0.89 s. FCP moved from 3.37 to 4.24 s and LCP from 3.67 to 4.30 s. Three samples per version and an unchanged comparison page supported withdrawing the change. This pattern is transport-dependent. See [Chrome Network timing](https://developer.chrome.com/docs/devtools/network/reference/#timing-explanation) for the browser measurements.

In a [category style trial](https://github.com/vibelingan/channel/actions/runs/44651155317), moving 60 KB of styles into the document and preloading one unchanged JPEG shortened the delay from the first HTML byte to image discovery from 477 to 50 ms. On four visits per version, median full-page LCP still rose from 4.23 to 4.48 s. In six alternating trials that served exact old and new HTML locally while downloading the same public assets, first paint improved in every pair. Hero paint was later in four pairs and the median rose from 2.666 to 2.798 s. One live trace showed the hero and the larger document bodies overlapping for 0.38 s. The trace shows overlap in that case. Confirm the cause of any other delay separately.

In a [subsequent controlled test](https://github.com/vibelingan/channel/commit/67027d0d2e4694942f4b30effa6c5fcff6ceef45), an Astro product route embedded the old product and category-page data ahead of the eager image even when the page already had its current approved product detail. Removing unused data put the same image 7.9–9.1 KB earlier in the built HTML. With identical image and stylesheet responses, alternating six times at each of two HTML transmission rates, median LCP improved by 46 ms at 200 KB/s and 160 ms at 50 KB/s. Keep these effects separate from production delivery and verify them again there. [Astro framework component props](https://docs.astro.build/en/guides/framework-components/#passing-props-to-framework-components)


## Upload and deploy incidents

**Prove what the provider received.** A browser sent a 4.81 MB PNG to Shanghai COS. One run succeeded after 155 seconds, mostly while sending. A later run returned HTTP 400 and reported `UserNetworkTooSlow` after about 203 seconds. The second attempt in that same run reached storage, but the browser test intentionally intercepted its success and failed to complete the UI. That mixed two failure modes. Keep the 4.81 MB case for measuring the actual network. Use a much smaller file that still takes the normal preview path for the lost-success test, intercept the first upload's success, then assert that retry uses one application record and does not resend known saved bytes. If assessing resumable uploads, check the provider contract first. Tencent's single presigned PUT has no resume operation. [Channel run](https://github.com/vibelingan/channel/actions/runs/44487251177) · [Tencent presigned upload](https://cloud.tencent.com/document/product/436/14114)

The corrected production test used a 200,514-byte PNG and hid exactly one real HTTP 200 response. The administrator clicked Retry once. The browser sent one PUT in total, the website kept one image record, the signed-in preview decoded, and anonymous access returned 404. An independent storage listing confirmed both test directories were empty after cleanup. This test answers whether the UI can recover a saved upload. Compare large-file first-upload throughput with matching workloads and networks. [Verified production recovery](https://github.com/vibelingan/channel/actions/runs/44495550172)

**Measure one version transition.** A Blog source upload took roughly 307 seconds to finish writing on the sender and received HTTP 400 at 311 seconds. The provider did not register a new version. A previously approved, byte-identical 7.20 MB video accounted for most of the archive. The shorter transfer sent the other files and let the cloud builder download the identical public video and enforce its length and SHA-256 before writing it. The full source archive still contained every file for recovery. The next provider reply was HTTP 200 at about 41 seconds, and its build took about 74 seconds. Verify the public version and a byte range of the video separately. In this case old and new responses overlapped briefly even after the provider reported the new version. Eight later article and image reads returned the new version. An unknown or changed video should still be uploaded in full. [Failed submission](https://github.com/vibelingan/channel/actions/runs/44482768619) · [Accepted submission](https://github.com/vibelingan/channel/actions/runs/44486733817)

**Keep authorization live when reusing image bytes.** A production public article API saved a repeated storage read by keeping only checksum-verified web derivatives in one function instance for a bounded time and size. Every response still checked the current article and image binding before and after selecting the bytes. Five of six consecutive HTTP reads bypassed storage, but only one of three fresh browser navigations did. Report actual hit counts and first-load timing. Verify older image URLs, an unavailable image, publication changes during a read, and object identity changes. Apply a shared cache policy only if it preserves the actual visibility rules and revocation timing. [Production run](https://github.com/vibelingan/channel/actions/runs/44499475494)

**Keep browser setup failures separate from page regressions.** In Channel, several browser jobs failed before any browser test ran. The Ubuntu index refresh had timed out, so APT reused package lists that named retired Mesa and GStreamer builds. The precise version mattered: the old Mesa `25.2.8-0ubuntu0.24.04.4` and GStreamer `1.24.2-1ubuntu0.6` objects returned 404. The current Azure Ubuntu mirror listed `25.2.8-0ubuntu0.24.04.5` and `1.24.2-1ubuntu0.7`; the same catalog checks installed them and ran successfully. The repair routed only the affected disposable runners to the reachable official mirror and made metadata refresh fail on an error. It preserved Ubuntu suites and signature verification, both browser engines, and the existing WebKit crash-dump safeguard. Compare runner image, package index and exact failing objects before changing tests or retrying every job. A prebuilt browser image can be useful when its browser versions and the suite's host requirements match. [Failed browser installation](https://github.com/vibelingan/channel/actions/runs/44524587152/job/135561908160) · [Verified installation and tests](https://github.com/vibelingan/channel/actions/runs/44526474715/job/135568457165) · [Official Playwright image contract](https://playwright.dev/docs/docker#image-tags)

**Use the part of the clock you can change.** Identify a case in which a repeated image read reached object storage before the proposed cache. Measure the same public URL, check the actual bytes and public state, and count storage reads with the same deployment and independent function instances. Report the first visit separately from cache hits. If a candidate cuts storage time in a repeated request, use cold-browser navigation to see whether visitors actually hit the same instance often enough to benefit. Keep every slower page sample and the server response budget. In particular a median of four lab samples cannot rule out occasional multi-second storage waits or establish field p75.

**Audit the production artifact before pruning.** Start from the accepted deployment receipt. Verify its archive digest and every manifest entry. Scan JS, CSS, and other published files for tests, source maps, example or fixture paths, embedded debug tooling, and generated inputs. Follow references from HTML, including CSS and JavaScript dependencies. A literal file graph can miss runtime-computed URLs. In Channel, a verified public archive contained 1,398 JS and CSS files. A literal graph rooted in current HTML reached 48; the release script had explicitly inherited assets from earlier releases for cached pages and restoration. Test current and previous HTML, dynamic imports, old tabs, and rollback at the chosen retention horizon before removing anything. Compare both compressed upload bytes and what a visitor actually downloads. [Accepted site delivery](https://github.com/vibelingan/channel/actions/runs/44653668498)

**Use initial JavaScript coverage to choose the next interaction to measure.** Match browser asset responses to the accepted archive before reading Chrome's coverage. Report decoded script size, actual transfer bytes, and bytes Chrome observed executing as separate quantities. Start on a cold navigation, then exercise the user action that can load or execute the suspected code. For a product page, include option selection, image zoom and opening the enquiry form. Initial unused code can support those actions. Attribute a real cost with a trace before splitting or removing it, and verify the production compression policy independently. [Chrome Coverage](https://developer.chrome.com/docs/devtools/coverage)

For the public delivery check, sample representative cold-browser journeys and hash the complete first-party script and stylesheet bodies. Compare them to the files in the accepted package for that page's actual service. Record files that do not match, which requests came from other services, and which interactions were outside the sample. A browser route may be a production 404 shell and still load valid assets, so check the main document and page identity too. Report decoded body sizes separately from the bytes sent over the wire.

Separate files copied from the build's public source directory from files inherited by the deployment step. Removing an unused source file prevents a clean build from copying it, while retiring a previously served URL requires its own compatibility check. In Channel, two videos absent from current HTML and literal script references still entered the clean build through `public/`. Git history showed they had been linked from earlier homepages. Compare the fresh build with the accepted archive and check prior HTML, direct public requests, and recovery before treating either file as removable.

**Verify which image the browser actually downloads.** A vendor listing can expose several size-specific URLs for one image. Inspect which attributes and layout slots refer to each size, fetch representative files with a normal public request, and record when rate limits prevent a byte comparison. A public URL cannot establish how the vendor retains its master internally. Compare actual response MIME and dimensions, since a `.jpg` URL can deliver AVIF. Record the exact viewport, page, matched image roles and body-size distribution. In Channel, a mobile browser loaded both a default image and a small version of the same thumbnail, and the page title painted while the rest of the gallery was still downloading. Compare actual selected URLs, request counts, complete transfer bytes and gallery readiness. For an image requested before scrolling, match its network initiator to the initial HTML and the element’s location. In one Channel trace the parser started the main image and four additional large originals used as thumbnails, even though the thumbnail elements used lazy loading. Resizing those slots addresses where the requests begin; changing the React prefetch further down the page would leave those parser requests in place. Serve a bounded web version for each layout slot, keep a larger version for explicit zoom, and retain the original with its existing access policy. Use HTML image discovery and the live access check in [technical SEO audit](../../technical-seo-audit/references/search-console.md) alongside the browser measurement. [Google image guidance](https://developers.google.com/search/docs/appearance/google-images) · [Alibaba OSS size contract](https://www.alibabacloud.com/help/en/oss/user-guide/resize-images-4) · [Verified Channel image sizes](https://github.com/vibelingan/channel/actions/runs/44721109221)

**Time source, storage, and verification separately.** Compare exact deployed source commits and workflow modes to determine whether a known optimization was present. In a 46-minute Channel run, prior optimization commits were present. A shared stylesheet received a new fingerprint. In the two accepted packages, 588 of 589 HTML files differed only in the stylesheet reference, so the release had to deliver almost every page. This caused about nine minutes of private recovery uploads and about thirty minutes of public delivery and verification after the build. Compare the manifest and, for an isolated hypothesis, normalize only that reference before comparing the complete HTML bytes. A 26-minute run uploaded one public batch and nine private packs; the 46-minute run uploaded 49 public batches and 33 private packs. Both ran 264 page checks. Record changed objects, reused packs, retries, and measured phase boundaries. Compare timing with releases that have similar input changes before changing the compiler or weakening verification. [Full catalogue HTML delivery](https://github.com/vibelingan/channel/actions/runs/44302615483) · [Single-batch delivery](https://github.com/vibelingan/channel/actions/runs/44137384987)

For a server-rendered application, scan the submitted application package separately from public browser assets. Verify a development marker corresponds to executable module code, then check the production branch selected by the actual runtime configuration. Channel’s Blog server bundle contained the development and production React implementations even though the container default selected production. That is application-package overhead. Establish any effect on response time or cold start independently, and keep it out of browser transfer totals. In a follow-up, a build-time production definition removed both React development branches. With the same source and environment, uncompressed server files went from 2,986,232 to 2,066,834 bytes. All seven browser files remained byte-identical. Both packages passed the standalone HTTP suite with public proxy images, direct API images, and preview indexing restrictions. In eight alternating local Node process starts, median time to a complete health response was 87.4 versus 85.5 ms, with overlapping ranges. Record this as a smaller deployment artifact. It does not establish a material improvement in production startup or visitor speed. [Blog build output](https://github.com/vibelingan/channel/actions/runs/44510561053/artifacts/14522561776) · [Production deployment](https://github.com/vibelingan/channel/actions/runs/44513022057)

**Recheck the full set of requests before choosing a media hostname.** A shorter individual request can lose once all images share the same connections. In Channel, a 5,964-byte thumbnail returned the same bytes from two hosts and had a faster median first byte on the site hostname. Replaying the same document with real network requests and four thumbnail URLs changed to that host made five visible thumbnails finish later in all four pairs. Preserve the single-file result and the page result. Record which part of the page the replay bypasses and keep the existing host unless a representative browser check supports migration.
